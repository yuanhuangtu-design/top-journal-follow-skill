# 日报自动运行的检查与恢复

文献检索、翻译和飞书同步在 GitHub 托管的执行环境运行。GitHub 内部的定时执行不依赖个人电脑开机。

## 什么才算当日日报完成

检查 `reports/latest.json` 与 `reports/search_progress.json`，需同时满足：

- 报告日期是北京时间今天，检索完整。
- 飞书同步核验成功，状态为 `ok` 或 `empty`，待写队列为 0。
- 中文标题没有待补项。
- 全部检索组的配置指纹与当前配置一致，进度覆盖到昨天。

没有新文献时，完整检索后的 `empty` 是有效结果。仅有一个绿色的只读连接检查，不代表当日日报已经执行。

## 当前时间安排

- 每天北京时间 05:17：执行日报。
- 每天北京时间 07:23、09:41：检查是否完成，未完成则补跑。
- 周日北京时间 05:30：生成周候选目录。

这三个日报时点共用 GitHub 的定时服务，只增加触发机会，不能作为三个彼此独立的兜底。GitHub 官方允许定时任务延迟，负载较高时部分任务可能被丢弃：

[GitHub schedule 事件说明](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)

## 如何区分哪里出了问题

1. 打开 GitHub 仓库 → Actions → Daily Literature Report。
2. 查看当天有没有运行记录；完全没有记录时，程序尚未启动，不能按翻译或飞书错误来排查。
3. 有记录时，查看 `Record trigger details` 步骤或任务摘要：
   - `event: schedule` 才是自动触发。
   - `event: workflow_dispatch` 是手动/API 启动。
   - `schedule` 表示命中的定时表达式，`started_utc` 表示实际开始执行诊断步骤的时间。UTC 加 8 小时为北京时间。
4. 有任务但失败时，查看失败步骤和 `feishu_diag`，区分检索不完整、翻译缺失、写入失败及报告保存失败。

诊断信息也会保存为工作流附件中的 `output/trigger_details.json`，不包含凭据。

## 今天没有启动时怎么恢复

在 Actions 中选择 Run workflow，分支选 `main`，`run_mode` 选 `daily`，日期留空表示北京时间今天。先确认没有同一任务正在运行，启动一次后等到结束，再核验当日完成条件。

脚本会用 PMID 检查整张飞书表，只创建缺少的记录，并保留原有阅读状态。失败候选会保存在队列中。手动启动仍然会执行完整日报，请避免短时间反复点击。

## 如何验证定时服务恢复

重新启用工作流后，`active` 只说明开关已开启。恢复是否有效，要以新的 `schedule` 运行记录为依据；手动测试成功只能证明执行流程可用。

需要临时自动测试时，将测试映射到 `check_connection`，避免重新写入文献；测试后删除临时时点。即使测试成功，也只能说明当次触发成功，不能保证未来每次都准时。

如果关机期间也需要独立兜底，应由另一个云端定时器检查日报是否完成，缺失时调用 GitHub 启动同一个工作流。文献处理仍可全部留在 GitHub。外部定时器应使用最小范围的授权，并在日报已经完成或正在运行时跳过启动。
