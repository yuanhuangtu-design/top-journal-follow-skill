# 新飞书组织的日报配置

原文献表导入新组织后，必须将下列四项仓库 Actions Secrets 配套更新：

| Secret | 内容 |
| --- | --- |
| FEISHU_APP_ID | 新组织中已发布应用的 App ID |
| FEISHU_APP_SECRET | 同一个应用的 App Secret |
| FEISHU_APP_TOKEN | 新组织导入后生成的多维表格 app_token |
| FEISHU_TABLE_ID | 新表中实际文献数据表的 table_id，不能使用页面的 wbp 标识 |

工作流将应用固定为 `cli_aa5219a0e079dbf6`，旧身份的 App ID 会被拒绝。表 ID 必须明确提供，不会自动选择第一个表。

先在新表「更多 → 添加文档应用」中授予该应用编辑权限，再运行 Actions 的手动任务，选择 `run_mode: check_connection`。此模式只读取完整表结构、PMID和已读数量，不写入记录。初次迁移应与原导出核对195篇文献和9条已读标记。

首次补录选择 `run_mode: sync_pending`，仅查重并补入已经保存的候选，不重新检索或翻译。定时任务默认 `daily`，继续执行现有五组检索。

正常运行按 PMID 全表查重，只新增缺失文献，不修改已有文献、笔记、已读状态或优先级。写完后重新读取并核实。分页失败、重复PMID或读回失败时不会报告完整成功。

`reports/feishu_pending.json` 保存等待确认入库的候选文献。恢复时将45篇历史候选与10月21日已生成日报合并为57篇待核验候选，实际新增数量由目标表查重决定。每次运行合并新候选，完整读取目标表后去重。网络超时不会直接重试新增；后续运行先重新查表，确认服务端已保存的条目后再清理队列。

应用还需开通 `base:record:retrieve`（根据条件搜索记录）才能完整查重；`base:record:read` 只允许按已知记录ID检索。新表为 `A0YXbg3tWat9LrsmCVHc78JHnSh`，文献数据表为 `tblaFUKHT1heqU4c`。迁移前已通过API确认195篇文献全部存在、9条已读状态与原始导出一致。

检索结果、同步诊断和待补录队列在写入失败时仍会上传，正常日报还会将队列和最新报告提交回仓库。任务失败并不意味着本次没有检索到论文；认证失败时，待新增数量会显示为未知。
