# 文献日报：本轮修复与后续迭代

## 先理解处理流程

把日报理解成三项独立工作：**找到文献 → 补全内容 → 写入飞书**。一项失败，不应抹掉其他已完成的工作。

- 找到文献：按期刊组、PubMed 入库日期（EDAT）检索，PMID 是每篇论文的唯一标识。
- 补全内容：批量获取原文资料，翻译标题、摘要。原文没有摘要和请求失败分别记录。
- 写入飞书：先完整读取已存在的 PMID；新论文新增，旧论文只补空白。已有中文、已读状态、日期、优先级与分数保留。

进度保存在 reports/pipeline_state.json。里面只存公开论文资料、翻译、失败日期和待补 PMID，不存飞书用户记录或凭据。请勿把本地飞书备份上传到仓库。

## 本轮改了什么，为什么

| 原问题 | 处理 | 你能看到的变化 |
|---|---|---|
| 请求过密产生 429，部分成功结果被整组丢弃 | 全部 PubMed 请求共用限速，批量取详情，有限重试 | 成功部分照常保留，失败日期/PMID 下次补抓 |
| 检索失败也显示成功、零篇 | 区分 ok / partial / failed，重要失败返回非零退出码 | GitHub 任务会明确失败，并保留已完成进度 |
| 翻译失败后过了检索窗口就不再处理 | 文献与分段译文持久缓存，跨日补翻 | 失败的摘要仍在队列里，不必重译已完成分段 |
| 摘要被硬切割，英文残留、数字变化难识别 | 按句/空格分段，检查中文比例、长英文片段、数字 | 不合格译文留空，等待下一次尝试 |
| 飞书读表失败仍继续新增 | 必须完整读取所有分页，查重成功后才能写 | 避免因部分查重结果重复插入 |
| 已存在论文一律跳过 | 只补空白字段 | 缺译文可补，阅读状态和手工改动保留 |
| recognition 被误判为 ecog，单复数重复加分 | 单词边界匹配，同概念合并，标题奖励只加一次 | 新增论文的排序更可信；旧表评分不自动重算 |

注意：翻译检查是质量筛选，不是医学或统计语义审核。优先级是关键词相关度，不是论文质量结论。

## 怎么验证自己的下一次修改

先运行自动测试：

```powershell
python -m unittest discover -s tests -v
```

再用独立状态文件试跑，避免改动正式进度；以下命令不会写飞书、不会调用翻译：

```powershell
python scripts/run_daily.py --date 2026-10-03 --start-date 2026-09-30 --no-translate --no-sync --state output/trial-state.json
```

运行日期表示日报日期，检索截止日是前一天。初次运行默认回溯至 initial_backfill_date；显式指定 --start-date 会覆盖这个初始值，但已有失败队列仍会补抓。不要删除正式 pipeline_state.json 来解决单次失败。

查看输出 JSON 和 GitHub 运行摘要：run_status、errors、pending_details、pending_translation、delivery。翻译待办不会阻止已抓到文献入库；检索/详情/同步错误会令任务失败，任务仍会尝试保存进度。任务被强制终止、存储或提交失败时，最近未持久保存的进度仍可能丢失。

## 推荐的下一轮改进

1. 先观察连续七天：每组新增数、重试数、待翻译数，以及你实际阅读的比例。
2. 若待翻译持续增长，再选择有预算控制的专业翻译/模型服务。不要先增加期刊数量扩大积压。
3. 用已读、收藏和“不相关”样本校准排序；研究设计、样本量、方法创新可单独展示，不与相关度混成一个分数。
4. 数据量更大后，把公开论文缓存迁移到数据库；保留 PMID 唯一约束、任务状态与重试次数。

## 当前边界

GitHub 同一日报工作流已串行执行；不要同时在本地与 GitHub 对同一表运行写入，外部并发写入没有数据库级唯一约束。免费翻译限额或持续不合格译文可能长期待办，需要人工处理。正常同步只补空白，不会自动替换已有错误译文；本轮已知错误使用单独定点修复。Notion 是保留的可选功能，尚未完成去重和长摘要展示改造，本轮重点验证飞书。
